# 03 · 如何读懂性能数据：延迟、吞吐、分位数与常见的坑

> **学习目标**：看懂延迟/吞吐/分位数指标，掌握正确的计时方法，识别对比实验中的不公平因素，拿到性能数据有一套提问模板。
> **前置知识**：读完 [01 · 量化入门](./01_quantization_basics.md)（理解延迟数字背后的模型差异）；建议读过 [02 · 硬件架构](./02_hardware.md)（理解为什么同一数字换机器就变）。
> **本篇不覆盖**：具体实验数据——全部数据见 [04 · 完整实验结果](./04_results.md)，本篇只教「怎么读、怎么测」。
>
> 本项目的基准测试走了不少弯路（修了 4 个 bug 才拿到可信数据），这篇把这些坑和正确的测量方法讲清楚。专业词随时查 [00 · 术语速查表](./00_glossary.md)。

## 1. 三类基本指标

| 指标 | 定义 | 什么时候看 |
|---|---|---|
| **单条延迟** | 处理 1 条数据的时间（ms/条） | 在线服务（用户等一条结果） |
| **吞吐** | 单位时间处理量（条/秒） | 离线批处理（跑完一个数据集） |
| **模型体积** | 文件大小（MB） | 边缘设备 / 下载分发 |

延迟和吞吐**不是倒数关系**：batch=1 的延迟低不代表吞吐高，批量并行时吞吐可以高很多倍（GPU 尤其明显）。所以本项目两个都测：batch=1 测延迟、batch=256 测吞吐。

## 2. 为什么要看分位数（P50/P95/P99）

P50/P95/P99 是把多次测量结果**从小到大排队后按位置取值**：P50 = 排在正中间的值（中位数），P95 = 95% 的请求快于此值，P99 = 99% 的请求快于此值。

只报平均值会掩盖长尾。本项目 CPU 延迟实测（200 次，batch=1）：

| 模型 | P50 | P95 | P99 | 结论 |
|---|---|---|---|---|
| fp32 | 0.592 | 0.640 | 0.708 | 稳定 |
| int8 静态 | 0.242 | 0.254 | 0.418 | 快且稳 |
| bf16 混合 | 20.9 | **67.1** | **85.0** | 平均值都救不了：P99 是 P50 的 4 倍 |

bf16 的 P99 长尾（85 ms）来自 P 核/E 核调度波动和仿真路径的缓存抖动——对在线服务这意味着 1% 的请求慢 100 倍以上，不可接受。**在线服务看 P95/P99，离线批处理看吞吐。**

## 3. 正确的计时方法（本项目的做法）

```python
# 1) 预热：前几次调用有 JIT/缓存/内存分配开销，必须丢弃
for _ in range(10):
    model(dummy)

# 2) GPU 计时必须同步：CUDA 调用是异步的，不同步会测出"发射时间"而非"执行时间"
torch.cuda.synchronize()
t0 = time.perf_counter()
for _ in range(50):
    model(dummy)
torch.cuda.synchronize()   # 没有这行，GPU 数字全是假的
elapsed = time.perf_counter() - t0

# 3) 多轮取分位数而非单次
```

三个细节：GPU 计时**先同步再掐表**；batch 越大迭代次数越少（控制总时长）；CPU 上混合架构（P/E 核）会导致波动，多轮测量取分位数。预热丢弃的是 JIT（即时编译——第一次运行才把代码编译成机器码，所以前几次特别慢）等一次性开销。

## 4. 本项目踩过的 4 个 bug（都是真实的坑）

**bug 1：bf16 模型把 BatchNorm 也转了**。BN 的 running_mean/var 对精度敏感，且与保留 fp32 的相邻层 dtype 不匹配直接报错。教训：**BN 永远保留 fp32**。

**bug 2：TRT fp16 引擎喂了 fp32 输入**。强类型引擎（构建时就锁死输入输出数据类型、不允许运行时改变的引擎）的输入输出 dtype 必须与引擎声明一致（fp16 引擎是 HALF），喂 fp32 导致精度静默丢失——准确率 99% → 54%，不报错、只掉精度，最危险的 bug。教训：**按引擎声明的 IO dtype 动态适配输入输出**。

**bug 3：QDQ 节点插到图最前面**。激活 Quantize 节点的输入是中间层输出，放最前面破坏拓扑序（模型图的执行顺序：必须先算出数据、才能执行消费它的节点），ONNX checker 直接拒绝。教训：**QDQ 必须插在消费节点之前**（就地重建节点序列）。

**bug 4：torchao int4 的 dtype 链路 bug**。zero_point 硬编码 bf16 与 scale fp32 冲突报错；统一成 fp32 又会被 kernel 误读（输出全错）。教训：**遇到版本组合 bug，用单层最小例子隔离**——我们用单层 Linear 的余弦相似度（0.998）确认数学正确，才定位到是打包格式问题。

## 5. 对比实验的公平性原则

1. **同一模型、同一数据**：所有精度都从同一个 fp32 checkpoint 出发，同一测试集评测；
2. **对照实验隔离变量**：2:4 稀疏实验构建了"同权重、开关 SPARSE_WEIGHTS"两个引擎，+6% 吞吐才能归因于稀疏 kernel 而非其他；
3. **随机波动要复跑**：TRT 基准跑了 6 轮才确认稳定区间（fp16 吞吐 22-35 万条/秒波动），单轮数字不可信；
4. **报告环境**：CPU 型号/GPU 型号/驱动/库版本全部记录（见 [04 · 实验结果](./04_results.md)），换机器数字会完全不同。

## 6. 读数据的思维模板

拿到一组性能数据，依次问：

1. **速度差是谁带来的**——精度（算得少）还是执行方式（开销少）？本项目 TRT 30-100 倍的差距主要是执行方式；
2. **这个数字在该硬件上是最优的吗**——查硬件-精度匹配矩阵（[02 · 第 4 节](./02_hardware.md)），bf16 在 CPU 上慢 40 倍不是 bf16 不行，是 CPU 没有 bf16 单元；
3. **精度损失在这个任务上可接受吗**——用最难的真实任务验证（Fashion-MNIST 教训：MNIST 上无损不代表难任务上无损）；
4. **长尾延迟是多少**——平均值好看不代表在线服务能用。

照着模板读完想核对原始数据？全部实验数字按主题整理在 [04 · 完整实验结果](./04_results.md)，可随时跳查。

## 自测：你学会了吗

<details>
<summary>1. 延迟和吞吐是什么关系？为什么本项目两个都测？</summary>

不是倒数关系。batch=1 的延迟低不代表吞吐高——批量并行时吞吐可以高很多倍（GPU 尤其明显）。在线服务（用户等一条结果）看延迟，离线批处理看吞吐。
</details>

<details>
<summary>2. bf16 混合精度 P50 只有 20.9 ms，为什么说它不能用于在线服务？</summary>

看分位数不看平均值：它的 P95 = 67.1 ms、P99 = 85 ms——1% 的请求慢 100 倍以上（P 核/E 核调度波动 + 仿真路径缓存抖动），在线服务不可接受。
</details>

<details>
<summary>3. GPU 计时为什么必须在前后各调一次 torch.cuda.synchronize()？</summary>

CUDA 调用是异步的：不同步，计时段里只包含「把任务发射给 GPU 的时间」而非真正执行时间，测出来的数字全是假的。
</details>

<details>
<summary>4. 为什么 2:4 稀疏实验要构建「同权重、只开关 SPARSE_WEIGHTS」的两个引擎？</summary>

隔离变量做归因：+6% 吞吐才能确定来自稀疏 kernel 而非其他因素。加上「复跑多轮确认稳定区间」「全部报告硬件环境」，构成对比实验的公平性原则。
</details>

<details>
<summary>5. TRT fp16 引擎喂 fp32 输入会发生什么？</summary>

精度静默丢失：准确率 99% → 54%，全程不报错。强类型引擎的 IO dtype 必须与引擎声明一致（fp16 引擎是 HALF），要按声明动态适配输入输出。
</details>
